## 2. Принципы работы

1. **Одна итерация = один смысловой коммит + деплой + проверка.** Не смешивать рефакторинг с
   исправлениями: иначе при откате теряются и фиксы.
2. **Сначала безопасность и падения, потом данные, потом UX, в конце — архитектура.**
3. **Каждый фикс закрывается тестом**, если его можно проверить без браузера (`node --test`).
   Фронтенд проверяю пробой в headless Edge (CDP), как делал раньше.
4. **Ничего не ломаем в работе читалки:** после каждой итерации `node --test` = 44+ зелёных,
   `node --check` по всем файлам, деплой, проба «лента открывается и не пересобирается».
5. **Секреты и пароли не печатаю** и не коммичу; в отчётах — только факты («файл отслеживается»).
6. Большие файлы (`reader-core.mjs` ~4.2 тыс. строк, `public/app.js` ~5.6 тыс.) правлю
   **точечными патчами**, без переформатирования и без смены окончаний строк (в `app.js` CRLF —
   уже один раз на этом спотыкался).

## 4. Порядок и зависимости

```
0 (секреты, краш) → 1 (SSRF, DoS) → 2 (XSS) → 3 (сессии, заголовки)
                                        ↘ 4 (данные, ядро) → 5 (деплой, инфра)
                                        ↘ 6 (фронтенд) → 7 (парсинг, тесты) → 8 (техдолг)
```

- Итерации 2 и 4 можно делать параллельно, если правки не пересекаются по файлам
  (XSS — `readability/comments/telegram/app.js`; данные — `store/reader-core`).
- Итерацию 6 нельзя начинать до 0–1: там правки `app.js`, а он же участвует в пробах.
- Итерация 8 — только когда 0–7 закрыты и есть 2–3 дня без релизов.

## 6. Совместимость API: что можно менять, а что нельзя

Решение принято: **API меняем только аддитивно**. Ниже — разбор по каждому
«ужесточению» из TODO: что именно сломается и как сделать то же самое, ничего не ломая.

| Изменение | Что сломается | Как делать безопасно |
|---|---|---|
| Требовать `Content-Type: application/json` на все POST | **Fever-клиенты** (Reeder, NetNewsWire, Unread, Fiery Feeds) шлют `application/x-www-form-urlencoded`; `lib/fever.mjs:25-28` разбирает именно форму. Плюс личные `curl`-скрипты и шорткаты. | Требовать JSON только для `/api/*`, и только если в запросе нет `api_key` и нет `Authorization`. `/fever`, `/`, форма — не трогать. |
| CSRF: отклонять POST без `Origin` | `curl`, скрипты, API-ключевые клиенты, расширения (у них `Origin` нет вовсе). | Отклонять только при `Sec-Fetch-Site: cross-site` — этот заголовок ставят браузеры, скрипты его не посылают. Дополнительно можно требовать JSON, как выше. |
| Перенести `api_key` из адреса в заголовок | Все Fever-клиенты: протокол передаёт ключ в query/теле. | Не делать. Поддержать и заголовок — как добавку, не как замену. |
| Поменять формат/параметры `/api/data` | Открытые вкладки со старым `app.js` из кэша SW и личные скрипты; при деплое старый клиент продолжает жить минуты-часы. | Только добавлять параметры и поля. Старые вызовы без новых параметров должны работать как раньше. |
| Починить `?api=1` в Fever (P1.15) | Ничего: сейчас `api=1` считается командой и обрывает ответ после лент, поэтому `?api=1&feeds=1&items=1` отдаёт только ленты. Это баг, а не совместимость. | Считать `api` командой только при совпадении с известным списком (`feeds/groups/items/…`), иначе — просто меткой. Клиенты получат больше данных, не меньше. |
| `sessionVersion` (P0.10) | Другие сессии после смены пароля потребуют повторного входа; Basic-Auth/API-ключевые клиенты со старым паролем перестанут работать. | Это и есть цель. Предупредить заранее и оставить `?api_key=` живым (ключ меняется только вместе с паролем). |
| `Cache-Control: no-store` | Ничего. | Делать. |
| `400/413` вместо `500` на битый ввод | Ничего (меняется только ответ на невалидный запрос). | Делать. |
| Ужесточение санитайзера, блокировка приватных IP, таймауты | Старые статьи могут потерять часть вставок; фиды, ведущие на `127.0.0.1`/LAN, перестанут обновляться; очень медленные видео обрежутся по таймауту. | Это задумано. Для видео таймаут ставим щедрый (20 с на подключение, без обрыва уже начатой передачи). |

**Правило проверки:** перед каждым коммитом с серверными правками гоняю матрицу запросов
(JSON/форма/`curl` без заголовков/`api_key` в query/`Origin` cross-site) — она должна давать те же
ответы, что и до правки, кроме случаев, ради которых правка делается.

## 7. Что нужно от вас

1. **P0.1 — по вашему решению не трогаем.** Ни пароль VPS, ни историю `watchfaces`.
2. Сказать, начинать ли с итерации 0 (краш-фикс, `parseCookies`, `publish.ps1`) —
   она короткая и почти без риска.
3. Предупредить, если у вас есть свои скрипты/шорткаты к API — учту их в матрице проверки.

## 8. Итерация 2 (XSS): проект правки, готовый к применению

Одобрение ещё не получено, поэтому код не менялся — ниже точный состав правки, чтобы
решение принималось по существу.

### 8.1. Серверный санитайзер `lib/readability.mjs` (P0.6)

Что не так сейчас:

- регэксп тега `/<([a-z0-9-]+)((?:\s+[^>]*)?)\/?>/` требует **пробел** после имени, поэтому
  `<img/src=x onerror=…>` проходит как текст, а браузер потом разбирает его как тег;
- разрешён `data:image/…` — включая `data:image/svg+xml`, где может быть скрипт;
- в списке удаляемых нет `base`, `object`, `embed`, `math`, `frame`.

Что сделаем:

1. Тег разбирать как `/<([a-z][a-z0-9-]*)((?:\s|\/)[^>]*)?>/gi` — тогда `<img/src=…>` попадает
   под allowlist и лишние атрибуты отбрасываются.
2. Список атрибутов (`KEEP_ATTRS`) не расширять; явно вырезать всё, что начинается на `on`,
   плюс `style`, `srcdoc`, `formaction`.
3. `data:` разрешать только `data:image/(png|jpeg|gif|webp|avif)`, `svg+xml` — запретить.
4. В список вырезаемых блоков добавить `base|object|embed|math|frame|frameset`.
5. Отдельная функция `sanitizeHtml(html, base)` (экспорт), чтобы её же использовать в комментариях.

### 8.2. Комментарии `lib/comments.mjs` (P0.7)

`text_template` от Tolstoy сейчас идёт в `html` без чистки. После правки: тот же
`sanitizeHtml` перед возвратом комментария; у остальных провайдеров — та же проверка
(они отдают уже готовый HTML).

### 8.3. Медиа-прокси `reader-core.mjs` (P0.5)

Для `/api/img`, `/api/thumb`, `/api/favicon`: allowlist типов `image/jpeg|png|gif|webp|avif`,
`X-Content-Type-Options: nosniff`; если апстрим отдал `image/svg+xml` или файл начинается
с `<` — отдавать как `text/plain` (или 415). Для `/api/video`: allowlist `video/*` и
`application/octet-stream`, иначе `text/plain`; `nosniff` тоже.

### 8.4. Клиент `public/app.js` (P0.8, P0.9)

1. `sanitize()`: удалять все `data-*`, **кроме** нашего `data-rss-embed`; переименовать
   атрибут плеера в `data-rss-embed`, чтобы статья не могла подделать «свой» атрибут.
2. `setupEmbeds()`: перед подстановкой `iframe` проверять `new URL(src)`,
   `protocol === 'https:'` и домен из allowlist (`youtube.com`, `youtube-nocookie.com`,
   `rutube.ru`, `vk.com`, `vkvideo.ru`, `dzen.ru`, `ok.ru`); иначе — не плеер, а ссылка.
3. `window.open(item.link)`: только `http(s)` через `safeHttpUrl()`; иначе ничего не делаем.

### 8.5. Тесты (до деплоя)

Набор payload'ов в `test/readability.test.mjs`:

```
<img src=x onerror=alert(1)>
<img/src=x onerror=alert(1)>
<svg onload=alert(1)></svg>
<a href="javascript:alert(1)">x</a>
<a href="data:text/html,<script>alert(1)</script>">x</a>
<img src="data:image/svg+xml,<svg onload=alert(1)>">
<base href="https://evil.example/">
<object data="javascript:alert(1)"></object>
<math><mtext><script>alert(1)</script></mtext></math>
<div style="background:url(javascript:alert(1))">x</div>
```

Ожидание: в результате нет `on\w+=`, нет `javascript:`, нет `<base|object|math`,
`data:` остаётся только для растровых картинок.

### 8.6. Риск для вёрстки

Санитайзер станет строже: часть старых статей может потерять вставки (`<iframe>` уже
заменяются кнопкой, а `<object>/<embed>` пропадут). Это осознанная плата; проверять будем
на живых лентах (Хабр, Mobile-Review, «Банкста», Telegram).
